## Migration guards and location

The SQL migration acquires table locks and performs preservation checks in the same transaction as its changes. It aborts on inconsistent/missing retained full names, unexpected secondary contacts, invalid location components, component conflicts with existing text, ambiguous/manual-clear backfill or a consolidated value exceeding 500 characters. It never prints conflicting candidate values.

Safe component-only locations are joined in city/region/country order. Existing complete locations and explicit manual clears are preserved. No employer/institution location is used. No statuses, revisions, confidence, verification records or provenance are recalculated or rewritten.

Future extraction retains existing candidate header/personal-location recognition, but emits only `locationText`. Separately labelled meaningful components are combined when a meaningful complete location is absent. Placeholder components are excluded. This is a representation adaptation, not the broader M3.6 accuracy work.

M3.4 uses persisted `locationText` exclusively. Its inclusive 75% complete-field and 85% missing-links thresholds, contact validation, confidence algorithm, duplicate detection and manual-review protections remain unchanged.

## Rollback/recovery procedure

1. Stop the web process and resume worker before recovery. Do not reset, reseed or reprocess the database.
2. Verify the dump and affected-record JSON against the SHA-256 digests in `verification.json`. Use PostgreSQL 17-compatible tools.
3. Restore `development.dump` into a **new empty local recovery database**, using `pg_restore --exit-on-error --no-owner --no-privileges`. Keep the original development database intact. When using container tools, transfer binary dump bytes through a Node child-process stdin or a binary file; avoid PowerShell text pipelines for the dump.
4. Compare all public table row counts and content hashes with `verification.json`, using the same ordered `row_to_json` queries implemented in `scripts/backup-m35.mjs`. Check primary fields, statuses, evidence, child relations and original removed values.
5. Recover the pre-cleanup code/schema/migrations from `source.zip`, including the saved uncommitted work. Regenerate Prisma Client against that old schema. The pre-cleanup migration directory must be used so deployment does not immediately reapply M3.5.
6. Point only the local development configuration at the verified recovery database and restart the matching application version. Retain both databases and the backup until recovery is accepted.

A later rollback preserving edits made after M3.5 requires a separately reviewed compensating migration/data merge. Restoring an old snapshot by itself would lose those later edits. Do not run `prisma migrate reset`, edit old migrations, or change migration-history rows manually.
