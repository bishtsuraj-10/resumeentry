# M3.2 candidate review workspace

The candidate detail page is a recruiter workspace with a sticky identity/action
header, a structured information panel and a private original-document panel.
Desktop panels scroll independently; a keyboard-operable width control adjusts
the split from 40–70%. Below 800px the panels stack, section links scroll
horizontally, and the header keeps document and review actions available.
Existing theme tokens and workspace components provide light/dark surfaces,
typography, spacing and focus indicators. No runtime dependency was added.

## Review workflow

1. Navigate among overview, summary/preferences, skills, employment, education,
   projects, certifications, links, languages/additional qualifications and
   provenance. Section links move keyboard focus to their destination.
2. Compare structured data with the original PDF. PDF.js renders locally from
   the authenticated `/api/resumes/[id]/file` endpoint with same-origin
   credentials and no-store caching. Page controls, zoom, an independently
   scrolling canvas and an original-document link are provided. Permission,
   transport, invalid-PDF and render failures have explicit recovery UI.
   Non-PDF documents retain the authenticated download option.
3. Expand an identity/profile/record editor only when needed. Each supported
   field has an explicit Edit button, its stored value and a verification label.
   The field selector is locked while a draft is pending; save or discard it
   before switching fields in that editor. Other editors can hold independent
   drafts. The summary/preferences editor is separate from contacts.
4. Save one selected field, including an unchanged value intentionally being
   verified, or use **Save pending corrections** to combine explicit drafts in
   one PATCH and one expected revision. No displayed, untouched values are sent.
   Existing partial-date, array, boolean and JSON validation is preserved.
5. A conflict keeps the draft. **Reload candidate** obtains the latest revision
   without unmounting existing editors. A failed reload also retains drafts and
   blocks saving until a successful refresh. An acknowledged save followed by a
   failed refresh is reported distinctly and also requires reload.
6. **Complete review** is enabled only after pending drafts have been saved or
   discarded and processing allows review. It submits only `completeReview`
   and `expectedRevision`; it does not claim verification of unrelated fields.
7. Navigation links, browser history navigation and page unload warn about
   drafts. Cancelling a navigation warning keeps the current candidate.

Missing optional values are informational. Explicit manual evidence wins over
machine confidence. An unverified field with stored confidence below 0.75 is
labeled uncertain; this is a parsing reliability cue, never suitability or
candidate ranking. Record-level `verifiedAt` means a record has human edits,
not that every field has been verified. The UI lists exact recorded paths.

The PDF canvas is a visual comparison aid. The accessible original-document
link remains available for selectable text and the browser's PDF accessibility
tools. The original download permission and server authorization are unchanged.

## Persisted data mappings

All values come from the existing detail API with `candidateInclude`. No schema,
migration, extraction-engine or production-data changes were made.

| Workspace section | Persisted backing |
| --- | --- |
| Header / primary identity and contacts | `ResumeExtraction.name`, `designation`, `email`, `phone`; `CandidateProfile.firstName/lastName`, `headline` and location as fallbacks; `Resume.status/fileType/fileName` |
| Extraction confidence | `ResumeExtraction.overallConfidence`; name/email/phone/designation field confidence remains separate |
| Overview / additional identity and contacts | `CandidateProfile.firstName`, `lastName`, `locationText`, `city`, `region`, `country`, `dateOfBirth`, `additionalEmails`, `additionalPhones`; `ResumeExtraction.otherEmails` is separately labeled |
| Summary and preferences | `CandidateProfile.headline`, `summary`, `objective`, `totalExperienceMonths`, `noticePeriod`, `employmentPreferences` |
| Skills | `CandidateProfile.skills` → `ResumeSkill.context/originalText/confidence/verifiedAt` → `Skill.canonicalName/category` and `SkillTerm.displayName`; shared taxonomy names/categories are not renamed |
| Employment timeline | `CandidateProfile.employment` → ordered `CandidateEmployment` records, employer/designation, location/type, partial dates/current flag, description, responsibilities and achievements |
| Education cards | `CandidateProfile.education` → ordered `CandidateEducation` records, degree/field, institution/location, partial dates, grade/scale and description |
| Project cards | `CandidateProfile.projects` → ordered `CandidateProject` records, role, description, dates, URL, responsibilities/achievements; technologies come specifically from `CandidateProject.skills` → `ProjectSkill.skill.canonicalName` |
| Certification cards | `CandidateProfile.certifications` → ordered `CandidateCertification` records, issuer, credential ID, issue/expiry date components and URL |
| Professional links | `CandidateProfile.links` → `CandidateLink.url/label/type` |
| Languages and additional qualifications | `CandidateProfile.additional` → ordered `CandidateAdditional.type/title/details`; language proficiency, awards, volunteering, publications, internships and qualifications retain their typed details |
| Exact field verification | Detail API `manualFields`, sourced from verified `CandidateEvidence.fieldPath` in HUMAN `ExtractionRun` records; basic paths do not use the extraction row ID |
| Extraction provenance | Existing authorized provenance API → `ExtractionRun.method/parserVersion/startedAt`, `CandidateEvidence.fieldPath/sourceSection/text/location/confidence/verifiedAt`; existing run/evidence pagination remains intact |

The detail read previously omitted persisted `ResumeSkill.originalText`; this
implementation adds it to the existing select. It is now available to editors
and source-wording disclosure. No source text is reconstructed or fabricated.

## Existing mapping limits

- The existing skill PATCH records skill-association verification and explicit
  original-text evidence, but does not create an exact `skills.<id>.context`
  verification path. A human-edited skill field without exact evidence shows
  **Field verification detail unavailable**; the UI does not invent that path
  or mark other fields verified.
- The detail API's manual-field snapshot is bounded to 100 HUMAN runs with up
  to 200 evidence entries per run. Older verification may require inspecting
  paginated provenance. Absence from that snapshot does not establish that a
  field has never been reviewed. Legacy review timestamps similarly do not
  supply exact field-level evidence.
- There is no independent language table: languages intentionally use
  `CandidateAdditional` with type `LANGUAGE` and typed details. No absent
  optional relation is inferred from resume text by the UI.
- The PDF.js worker is vendored from the already installed PDF.js package at
  `public/pdf.worker.min.mjs`, retaining its Apache-2.0 notice. Keep it in sync
  with `pdfjs-dist` when upgrading; ESLint excludes this generated vendor file.

## Verification

`node scripts/verify-candidate-workspace.mjs` creates a randomly named
disposable database on a loopback PostgreSQL server. It runs the **complete**
Vitest suite with M1/M2/M3 integration opt-ins, applies existing migrations to
that new database, seeds only synthetic fixtures, starts the production Next
server and performs real Edge browser checks against actual authentication,
authorization, candidate APIs and private storage. It then removes its own
database and temporary files. It never seeds the configured application DB.
`--browser-only` reruns the live browser checks without repeating Vitest.
Run `npm run build` first. A PostgreSQL account allowed to create a disposable
database and local Microsoft Edge are required.

The live harness uses `localhost` consistently for the server and browser:
Next's route request URL uses that canonical host here, and the existing origin
guard rejects otherwise equivalent loopback hostnames. No origin protection was
disabled for verification.

`node scripts/candidate-workspace.browser.mjs` additionally exercises real
React/CSS/PDF.js with synthetic API contracts, including failed reloads,
cross-section draft batching, preview failures, empty sections and loading
failures. It does not replace live authentication/database checks.

Results are saved in `docs/evaluation/M3.2-tests.json`,
`M3.2-browser.json`, `M3.2-live-browser.json`, `M3.2-desktop.png` and
`M3.2-mobile.png`. The final implementation was also checked with
`npx tsc --noEmit`, `npx prisma validate`, `npm run lint` and `npm run build`.
