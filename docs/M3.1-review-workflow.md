# M3.1 review workflow and extraction evaluation

Implemented on `main`; no commit or push. Existing M3 work and synthetic fixtures were preserved. No schema change, production data change, candidate refresh, database reset, truncate or reseed was performed. Evaluation only read matching local candidates; integration tests created and removed separate synthetic schemas. No remote or paid AI was used.

## 1. Detail-page crash

The client chained `.catch()` onto the return value of route `params.then(...)`. Next supplies an awaitable route-parameter object whose `then` need not return a native Promise; in the reported environment it returned undefined. The server page now awaits `params` and passes an ordinary `id` to the client. Client loading uses `async`/`await`, HTTP/JSON checks and AbortController cancellation, with separate loading, missing-data, permission failure and retry states. Late loads cannot replace another candidate. Save requests are cancelled on navigation. Authentication, PageAccess and API permissions remain enforced.

Regression coverage includes a route thenable whose `.then()` returns undefined, failed/null responses, aborted loads, real component navigation and conflict handling.

## 2. Candidate review page

The page reads actual M2 CandidateProfile relations and legacy ResumeExtraction contact fields. It displays identity, contact, location, headline, summary, objective, experience, notice period, preferences, skills/categories/context, employment responsibilities and achievements, education, projects/technologies, certifications, links, languages and additional typed records. Missing information has explicit empty states. Dates preserve partial precision.

Confidence and human-edit markers are separate. Protected original-document links obey file permission checks. Authorized editors can open paginated extraction runs and source evidence. The default detail response includes bounded verified field paths without private source excerpts. Completion of a review is a workflow action; it does not claim that every field is verified.

Editors submit only the selected field. Existing row IDs are preserved, unrelated fields and records are untouched, and revision conflicts keep the draft with recovery guidance. Skill association additions/removals are supported. Other structured sections currently support correcting existing records rather than a complete add/delete/reorder interface. Review status is not automatically cleared by a single correction.

## 3. Recruiter tables

All Resumes and Review Queue show candidate name and filename, email, phone, designation, location, experience, up to five skills, highest identified education, extraction confidence, processing status, created date and View/Review action. Responsive tables scroll horizontally. Search, pagination, status filtering, export, permission checks and URL navigation are retained.

The list API uses one batched Prisma relation selection and count, selecting small profile/contact fields, five skill names and bounded education descriptors. It does not load employment/project histories or source evidence per row. Education is ranked only from extracted degree data. Filenames are not used to infer qualifications. Structured name/headline fallback respects legacy manually cleared values.

## 4. API compatibility

Existing structured GET/PATCH, optimistic `expectedRevision`, owned record IDs, correction precedence and provenance contracts remain supported. The legacy four-field PATCH is unchanged. The candidate PATCH accepts two optional additions: `basic` (partial name/email/phone/designation) and `completeReview: true`. These use the existing serializable revision transaction, preserve confidence and unrelated values, and record only submitted fields as human corrections. Basic/status edits reject active processing and cancellation. Completion requires an extraction and preserves duplicate status. Existing clients need not send the new properties.

Validation responses now include safe field paths and messages. HTTP 409 explains a stale revision instead of silently overwriting another review. Manual field metadata in the detail GET is bounded; extensive older audit history remains available through paginated provenance.

## 5. Extraction findings and fixes

Hash matching found all 20 stored records from the synthetic corpus, all on `local-comprehensive-v1`, all REVIEW, with no human edits detected. Local review threshold was 75%. Missing names/roles and unresolved employment legitimately triggered review, while layout uncertainty alone also triggered review regardless of 94% basic confidence.

Anika's complete specialty/seniority title was outside the narrow role dictionary. Sofia's large scanned name was lost by OCR segmentation; the UI substituted “Needs review” for missing identity. Rafael's unsupported “Civil Engineer” role was accepted as a name after his scanned header was lost. These were reproduced in parser output and stored fields; the batch showed no separate persistence mismatch for the measured fields.

General fixes recognize bounded complete role headers, exclude roles from names, use automatic local OCR segmentation with bounded page rendering, preserve column reading order, recognize common section aliases, reconstruct wrapped links and bullets, parse table/labelled employment and certification fields, retain explicit domain skills, and normalize language proficiency. New parser version is `local-comprehensive-v1.1`. Layout diagnostics remain visible but alone do not mandate review; unreadable pages, low OCR confidence, unresolved/invalid data, missing basic fields and below-threshold confidence still do. On this corpus the corrected parser projects no review requirement under those rules; this describes basic extraction confidence, not human verification of every structured field.

## 6. Read-only ground-truth evaluation

Run `npx tsx scripts/evaluate-synthetic-batch.ts --reread`. The evaluator verifies fixture SHA-256 hashes, checks ground truth remains unchanged, refuses non-local database hosts, and uses a read-only database transaction. It never queues jobs, retries or updates candidates. Raw documents are not logged. Temporary synthetic reader caching is outside the repository and is opt-in for reuse.

Reports: [before](evaluation/M3.1-before.json), [after](evaluation/M3.1-after.json), [browser checks](evaluation/M3.1-browser.json). Each extraction report contains per-field TP/FP/FN, missing field counts, precision/recall, document errors, coverage and stored parser/review metadata. Scores are exact normalized value-set matches, not fuzzy matches or record association accuracy.

Actual PDFs now recover 20/20 names, emails, normalized phones, full designations and headlines. Original name extraction had 18 correct, one wrong and one missing; full designations had eight exact, three wrong and nine missing. Employment employers, roles and partial dates match all expected values; degrees/institutions/end dates/grades also match. Coverage includes 61 jobs, 25 education records, 40 projects, 44 certification candidates, 79 links, 270 skills and 95 additional entries; coverage counts are not correctness claims.

Remaining exact errors include four missing summaries, one missing structured location, one education field of study, certification splits/issuers/dates, one missing URL, skill alias/context differences and extra additional titles. The ground truth's additional-title metric includes languages while the parser also correctly retains volunteering/contributions, so some counted false positives are valid extra document content. All 20 total-experience values differ: existing interval calculation excludes the in-progress month while ground truth counts it inclusively. This convention was not changed merely to improve accuracy. Authored transcript order can differ from spatial PDF order; the lower transcript score exposes layout-sensitive parsing rather than proving OCR is universally more accurate.

## 8. Refresh and remaining limitations

The structured persistence policy first-fills CandidateProfile and sections and protects human corrections. A worker restart or retry is not a safe way to replace this batch, and existing REVIEW records intentionally remain unchanged. The new UI therefore still displays the actual stored older values until an authorized reviewer corrects them.

Proposed explicit refresh: select a synthetic hash-matched batch; re-extract into an in-memory preview; show per-field and per-record differences; capture expected revision and verified field paths; require approval for selected changes; apply in an ownership-safe transaction that skips human-verified/deleted values and appends an auditable extraction run. Preserve legacy `reviewedAt`, section deletion precedence and M1 claim cancellation. Never bulk replace profiles or use a reset/reseed. This refresh command is a proposal, not an implemented or executed mutation.

Further work includes defining experience-month convention, improving certification grouping and multilingual OCR, adding full structured-record creation/removal controls, and authenticated end-to-end testing with an authorized test account. Basic confidence does not measure every structured field; inspect evidence and exact metrics before treating candidates as verified.
